**Goal:** Prove or disprove, within a $50 cap (planned: $14.68) (amended 2026-11-23, R75), that the pipeline can turn online photos into an E46 M3 exterior, a driver's-seat interior and one parametric wheel that meet spec section 9.9, and end with a spike report and ADR 0015.

**Architecture:** Seven new registered stages (`synth`, `proportion`, `generate`, `segment`, `cleanup`, `export`, `score`) share small tested libraries in `stages/lib/`. Each stage reads a hand-written `plan.json` in `<work_dir>/assets/<asset>/<stage>/`, so what runs and what is paid for is explicit. Headless Blender 5.2.3 scripts only apply a plan that Python computes and tests. A throwaway local three.js viewer proves that paint, glass, wheels and interior change separately.

**Tech Stack:** Python 3.14 + uv (Typer, pyyaml, plus the photo-tooling lane's pydantic, httpx, Pillow; one new pin, numpy), Codex CLI on the user's subscription (view synthesis and vision critic), fal queue API (generators), Blender 5.2.3 LTS, Node 26 with glTF-Transform 4.5.1 and meshoptimizer 1.3.0, three.js 0.187.0 from a CDN import map.

**Spec:** `docs/superpowers/specs/2026-11-23-m3-tool-design.md` (sections 3, 9, 10, 12, 15). Also ADRs 0004, 0005, 0006, 0012, 0013 and `docs/standards/{3d-assets,legal,code,testing}.md`. Inputs: the approved photo-tooling plan `2026-11-23-phase-0b-photo-tooling.md` (view sets, Task 8) and the generator research in `.superpowers/research/2026-11-23-generator-inputs-and-terms.md` (endpoint ids, prices, inputs, terms). That file is git-ignored and lives only in the main checkout, so a worktree does not have it: Tasks 7, 11 and the budget carry every fact they need.

## Global Constraints

- Python `>=3.14,<3.15`, uv. ruff 0.17.6, pyright 1.1.414 strict, pytest 9.2.0, Typer 0.29.2, pyyaml 6.0.4. The photo lane adds `pydantic==2.14.4`, `httpx==0.28.1`, `pillow==13.0.0`, `imagehash==4.3.2`. The only new dependency here is `numpy`, pinned exactly in Task 1 (2.5.5 today: imagehash already locks it). No other new Python or npm dependency. If a pin does not resolve, stop and report.
- Blender is 5.2.3 LTS, headless: `blender -b -P script.py -- args` (binary from env `M3_BLENDER`, else `blender` on PATH). Blender works in Z up with the nose toward +Y; the glTF exporter turns that into the contract frame (Y up, nose toward −Z). Python-side math, every plan's meaning and every GLB are in the contract frame. Blender scripts see only Blender-frame numbers for anything spatial (positions, directions, boxes, per-axis scales), under plan keys that end in `_blender`; non-spatial values (ratios, triangle counts, color thresholds, texture sizes) carry no suffix, and the wheel's `wheel-spec.json` (sizes in inches and mm) is not a frame plan. The boundary conversion is `frames.py` (Task 3): `(x, y, z)_contract → (x, −z, y)_blender` for points, directions and boxes. Proxy `.npz` files written by Blender stay in the Blender frame, and `load_proxy` converts them.
- Contract (spec 9.6, `src/lib/asset-contract.ts`; this plan never edits it): meters, Y up, nose toward −Z, origin on the ground under the middle of the wheelbase. Base car: nodes `body`, `bumper_front`, `bumper_rear`, `trunk_lid`, `roof`; anchors `wheel_FL`, `wheel_FR`, `wheel_RL`, `wheel_RR`, `mount_front_lip`, `mount_trunk`, `mount_wing`, `mount_exhaust_L`, `mount_exhaust_R`, `mount_interior`; materials `paint`, `glass`, `trim`, `lights_front`, `lights_rear`; 100k–200k triangles, ≤ 8 MB, textures ≤ 2K (4K for `paint`). Interior: nodes `interior` (the one root), `cabin_shell`, `dash`, `console`, `door_L`, `door_R`, `seat_driver`, `seat_passenger`, `steering_wheel`; anchors `mount_seat_L`, `mount_seat_R`, `mount_steering`, `camera_driver_eye`; ≤ 150k triangles, ≤ 6 MB, textures ≤ 4K. Product: one root, pivot at its anchor, ≤ 30k triangles, ≤ 1 MB, textures ≤ 2K. Required names are unique, anchors are empty leaves.
- Export (spec 9.5): weld, dedup, `prune({ keepLeaves: true, keepSolidTextures: true })` (amended 2026-11-23, Task 4 notes: the call as built, a deviation from spec 9.5's plain `prune`), meshopt. KTX2 deferred to Phase 1 (spike uses WebP/PNG). Never `optimize`, never `flatten()` or `join()` without `cleanup: false`. Then `pnpm validate-asset`.
- Money: key in env `M3_FAL_KEY` only; never `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`. Cap `$50` total for the spike, planned ≤ $25. Every paid call needs a session-approved cap and its row in `docs/spend-ledger.md` before the call. The guard (Task 2) enforces it in code: under an exclusive file lock, against a spend journal at a fixed path outside `work_dir` (`~/.local/state/m3-tool/spend-journal.jsonl`), and only when env `M3_SPEND_SESSION` equals the session label on today's cap row. The orchestrator sets that variable only after the user approves the cap in that session. Subscription (Codex) use has no ledger row.
- Generator inputs: every photo records its license, author and URL for provenance, and the spike gates nothing on which models or assets can be published (a later 3D-lane decision). People and number plates are masked or cropped, and each image is reviewed, before it is uploaded to a generator vendor (fal and its partners) or used as a synthesis input. Proposing redaction boxes on a photo itself, with Codex or the orchestrator's own vision, is allowed for any Commons photo in the view set: it is public already, whatever its license.
- Generator terms: Hunyuan 3.1 Pro (`fal-ai/hunyuan-3d/v3.1/pro/image-to-3d`) never runs on an EU, UK or South Korea host (Tencent's territory limit; `experiment_only` is recorded in `candidates.json` as provenance, never enforced). Never call the fal-hosted open-weights Hunyuan v2 endpoints. Hi3D (`hitem3d/*`) is excluded. Download fal results immediately: the queue keeps a result 1 hour, or 6 minutes for a large one.
- No BMW logos, badges or roundels in any mesh or texture, including the steering-wheel roundel and the gauges. A wheel center cap is plain or absent.
- Photos, generator outputs and renders stay in `work_dir` (`M3_WORK_DIR`, default `~/.cache/m3-tool`), never in the repo. Stages refuse a `work_dir` inside the repo. Tests build images and GLBs in code.
- Do not modify `pipeline/src/m3_pipeline/refs/*` (the photo lane owns it). Do not edit `src/data/schemas.ts`, `src/lib/asset-contract.ts` or `docs/standards/3d-assets.md` (contract PR only). `pipeline/pyproject.toml` is edited only in Task 1, after the photo-tooling PRs merge.
- Code standard: side effects (subprocess, network, Blender, node, Codex) sit behind injectable module functions, and no pytest test starts Blender, node or Codex or touches the network. Strict pyright; untyped data parsed into typed shapes at the edge. Spec section 10 says Blender stages run on a small fixture model; the code standard says no test starts Blender, and AGENTS.md wins over the spec. So Python computes and tests every plan, and each Blender script is verified by a recorded manual run on `make_fixture_car.py`. Every Blender script starts with `# pyright: basic, reportMissingImports=false`, because `bpy` is not installed in `pipeline/`'s environment and `pnpm check:pipeline` runs pyright over `pipeline/blender/` too; `pyproject.toml` stays untouched. - Commits: Conventional Commits, staged by path, never `git add -A`. The only trailer allowed is `Co-Authored-By:`. No `Claude-Session` trailer or session URL in a commit or PR. gitleaks runs in the pre-push hook. No image, GLB or `.env` is tracked.

- **Landing, tooling tasks** (anything with tests): `git worktree add ../m3-tool.worktrees/<slug> -b feat/spike-<slug> origin/main`, `pnpm install`, `uv sync --project pipeline`; inner loop `pnpm check:pipeline`; before every push `pnpm check` exits 0 and, after `pnpm build`, `pnpm e2e` exits 0 (AGENTS.md); push, PR from the template with `Refs #6` and the lane "3D"; review; squash-merge. **Experiment steps** run in one long-lived worktree `../m3-tool.worktrees/spike-run` on branch `spike/run`, rebased onto `main` before each stage run. ## Review Focus

Failure modes the spec implies and no happy path covers, most likely first. Each has a named test in its owning task.

1. A paid call that fires twice or loses its result: two processes racing for the last affordable row, a second session on the same day, a changed `M3_WORK_DIR`, a submit timeout, a crash between authorize and call, a download failure after payment, a rerun of a finished plan. Expect one tag to authorize one call, no authorization without the session's own cap row, no re-submit on timeout, result URLs kept for a download retry, finished calls skipped. Task 2 `test_tag_can_authorize_one_call_only`, `test_authorization_survives_a_crash_before_the_call`, `test_two_concurrent_authorizations_for_the_last_affordable_row_let_exactly_one_succeed`, `test_same_date_but_a_different_session_is_denied`, `test_default_journal_does_not_depend_on_m3_work_dir`; Task 7 `test_submit_timeout_is_not_retried`, `test_download_failure_keeps_result_urls_and_never_resubmits`; Task 11 `test_calls_already_in_candidates_json_are_skipped`.
2. A photo the rules forbid reaching an upload: a person or plate not reviewed, an image whose redaction file is missing. Expect a refusal that names the image id and no upload. Task 0 `test_require_generator_inputs_names_every_unreviewed_or_unredacted_image`; Task 10 `test_unreviewed_image_is_never_prepared_for_upload`.
3. A synthesized side view that fools the proportion check: car touching the image border, background that is not one flat gray, car cut in half by a crop. Expect a failed check, never a pass by default. Task 8 `test_silhouette_touching_the_border_is_rejected`, `test_non_uniform_background_is_rejected`.
4. A generated mesh that is rotated, mirrored or mis-scaled, and door mirrors that inflate the width (the data's 1,780 mm is without mirrors). Expect the width measured below mirror height, a refusal when axis scales diverge by more than 5%, an orientation that puts the nose toward −Z, and one frame conversion between Python and Blender. Task 3 `test_body_width_ignores_door_mirrors`, `test_contract_to_blender_round_trips_points_directions_and_boxes`, `test_axis_scales_refuse_a_divergence_over_5_percent`, `test_propose_orientation_finds_up_and_nose_for_every_axis_permutation`.
5. Codex or the critic answering with prose, an empty message, a half-formed JSON or `pass: true` next to a blocker. Expect a failed verdict, never a pass. Task 5 `test_garbage_message_is_a_failed_verdict_not_a_pass`, `test_pass_true_with_a_blocker_issue_is_not_ok`; Task 14 `test_critic_failure_is_a_failed_round_not_a_pass`.

**Interfaces:**
- Consumes: `Settings` (`config.py`).
- Produces:
```python
# paths.py
def stage_dir(settings: Settings, asset_id: str, stage: str) -> Path   # <work_dir>/assets/<id>/<stage>, created; ValueError if work_dir is inside repo_root
def subject_body(subject: str) -> str                                  # "e46-coupe" and "e46-coupe-interior" -> "coupe"; ValueError for any other shape
def require_outside_repo(repo_root: Path, path: Path) -> None                       # (amended 2026-11-23, Task 0 notes) ValueError if a write at `path` would land in the repo, links followed; pass the full destination of every write and directory creation
def require_write_target_outside_repo(dest: Path, repo_root: Path) -> None          # (amended 2026-11-23, Task 0 notes) the same for a file about to be written: it checks where the write really lands (resolved parent plus name). The two take opposite argument orders and a swapped positional call is silently allowed, so call both with keyword arguments only: `require_outside_repo(repo_root=..., path=...)`, `require_write_target_outside_repo(dest=..., repo_root=...)`
```
